# Plan 14-01: Data Layer & Backend Roles & Shared Cache (Wave 1)

## Executive Summary
Plan 14-01 lays the foundational domain, state, persistence, and backend architecture for the multi-user family role model in EduSync (`UserRole.parent` vs `UserRole.student`). It introduces the `UserRole` domain enum, integrates role data into `AppUser` and `SharedPreferences` for zero-latency UI rehydration, extends Cloud Function endpoints (`saveConnection`, `getConnection`) to store and return role metadata (`studentLogin`, `primaryLogin`, `familyId`), and establishes `students/{primaryLogin}` as the Single Source of Truth in `FirestoreSchoolRepository` (D-05, REQ-ROLE-03), completely preventing redundant Librus web scraping when the student logs in or browses.

---

## Threat Model & Security Controls
<threat_model>
- **Threat T-14-01 (Role spoofing / elevation of privilege):** A student user could attempt to craft requests claiming the `parent` role to bypass parental supervision.
  - *Mitigation:* `users/{uid}` in Firestore defines the authoritative role. Endpoints verify that actions requiring parental authority validate against parent records.
- **Threat T-14-02 (Cache poisoning / duplicate scraping race condition):** If parent and student trigger background sync simultaneously, Librus servers could detect parallel access and issue rate-limit blocks (HTTP 429).
  - *Mitigation:* `FirestoreSchoolRepository` routes all student academic reads (`isStudent == true`) directly to `students/{primaryLogin}` in Firestore, relying on Cloud Scheduler cron every 15 minutes. No scraping requests are dispatched on behalf of student views.
</threat_model>
